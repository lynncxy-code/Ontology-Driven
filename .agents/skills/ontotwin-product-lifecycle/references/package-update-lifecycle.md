# 接入包、导入更新与数据保留

## 适用范围和能力状态

用户已确定的方向：固定安装环境，通过“导入更新包”协调前端、后端与 UE 插件更新，保留原有数据；优先做好本地离线交付，不以建设中心后端为前提。

本文是后续开发和验收规范，不代表功能已经实现。历史 RC16 的运行配置位于解压目录 `.runtime`，新目录会创建新环境，跨源码版本会拒绝复用配置；它不是完整的持续升级器。后续先检查实际源码和包清单，再判断缺口，不把历史结论当成永远有效的现状。

## 发布形态

### 用户确认的打包约束（2026-11-02）

- RC20 暂不使用，仍有缺陷待修；保留已有包和修复记录，不将其作为当前推荐部署版本。
- 后续修复先完成实现与验证，不自动生成新的接入包；等用户明确要求打包时再执行。
- 下一次新接入包必须包含部署管理器及其入口、依赖和版本清单，不能只交付前后端与 UE 插件，或仅指向独立部署器下载。
- 打包时核对部署管理器所在分支的实际实现，将其纳入同一交付清单，并验证它与本次目标接入版本的组合。既有 RC16 → RC19 升级测试不能替代对新版本的数据与绑定保留、备份和失败恢复验证。

- 完整接入包：供新电脑首次安装，包含平台前后端、UE 插件、所需离线依赖、安装工具；默认不含客户 UE 工程和客户数据。
- 更新包：用于已安装环境，只携带变化组件、必要的数据升级脚本和兼容性信息。人物、行为及大型素材库未变化时无需重复传输。
- 两种包从同一个已提交、可追溯版本和发布清单生成，不维护两套实现。候选包与正式发布按主 skill 的晋级规则区分。
- 发布清单记录源码提交、发布版本、各组件版本/哈希、镜像身份、支持的 UE/平台与数据库版本、可升级的来源版本和迁移要求。组件版本号不必相同，但组合必须经过验证。
- 源码、编译后的插件和后台镜像必须与清单一致。压缩包完成后再次验证内容、校验和；测试产生的 `.runtime`、凭据、客户数据和临时验收工程不得混入发布包。

## 安装环境与程序分离

- 环境编号、端口、凭据、数据卷归属及当前/上一版本记录独立于版本解压目录保存。升级沿用原环境；清理旧程序目录不得删除业务数据。
- PostgreSQL、图数据库、文件存储及模型存储归属于固定环境。不得因更新版本生成空库替代原库，也不得仅凭端口可通或工程 ID 相同就复用未知旧库。
- 普通更新保留数据集、类型/实例、账号权限、UE 工程/关卡绑定、CAD、图片底图和上传模型。升级不会自动激活其他项目或改变关卡绑定。
- 新装、升级、恢复时先核对目标机器、UE 工程、后台地址、环境归属和数据集身份。种子包指纹用于核验导入来源，不能把后续正常业务编辑误判为数据损坏。
- 客户资产和自定义配置不作为标准程序覆盖。发现同名修改、插件 junction 或多个工程共享母本时，展示实际影响范围，依照用户选择处理冲突。

## 导入更新包的用户流程

部署管理入口优先显示：当前版本、目标版本、后台状态、关联 UE 工程、最近备份时间；主要操作为“启动平台”“导入更新包”“备份与恢复”。不要把 Docker 命令或数据库参数变成普通用户的必填步骤。

“同步更新”指一次协调流程达到兼容组合，不是边运行边强行替换所有组件。执行顺序：

1. **预检和暂存**：核验包完整性、升级路径、磁盘空间、数据结构版本、安装身份和前后端/插件兼容性，展示实际变化与受影响工程。预检不改变运行版本或业务数据。
2. **确定工程范围**：按用户选定的 UE 工程更新，保留已有选择。检查共享同一后台的未选工程是否仍兼容；不兼容时先解决升级范围或隔离环境，不能静默使其失效。
3. **满足更新条件**：需要替换插件时等待对应 UE 工程关闭。若共享插件文件被其他进程加载，也须处理。需要协调替换的组件尚未就绪时，停在“等待关闭工程”等明确状态，不先更新后台留下不兼容插件。
4. **备份与升级**：在明确的维护窗口暂停相关写入，取得数据库与文件的一致备份；备份验证成功后，按清单升级程序和数据结构。已有版本目录保留用于恢复。数据库版本升级与重新初始化空库是两件不同的事。
5. **校验和完成**：检查实际运行版本、登录、原数据与文件可读、权限、绑定及 UE 数据加载。旧实例、资产引用和项目身份符合预期才算通过；合法空数据集不应仅因实例数为零判失败。需要 UE 重启验证时显示“待重启验证”，不能提前显示完整更新成功。

升级过程记录步骤、备份位置和失败原因，防止同一环境并发升级；中断后从已记录状态判断安全续跑或恢复，不盲目重放数据库迁移。重试不能以删除数据卷、重建凭据或跳过兼容性检查为手段。

## 备份、换机与失败恢复

- **原机升级**：保留环境身份与存储，替换程序并执行已验证的迁移。
- **换机继续使用**：完整接入包配合环境备份恢复；重新核对本机路径、端口和工程映射。复制 ZIP 不会搬走 Docker 数据卷；两机副本也不代表自动双向同步。
- **只交付一个项目**：导出/导入数据集包。`.otdataset` 不默认等于全环境备份，不能宣称它已包含所有账号、权限、配置和文件。
- 环境备份明确覆盖数据库、图数据、CAD/图片/模型文件、账号权限、绑定及必要配置，保存版本与校验清单。凭据和备份按私有环境材料保护，不进入通用发布包或 Git。
- 数据结构变更联动 `ontotwin-db-migration`，记录已应用迁移；在一次性副本上验证升级及恢复，不能用“已登记备份”代替“确实能恢复”。
- 无数据变更且兼容时，可切回上一程序/插件组合；涉及数据结构变更时按已验证方案恢复。需要恢复旧数据备份时，明确恢复时点和升级后新增数据的影响，在该影响未获授权时不要自动覆盖。
- 更新失败显示实际状态，保留诊断日志与恢复入口；不能把一部分组件成功更新标为整体成功，也不能反复尝试破坏性的重置。

## 最低验收与交接

根据本批变化验证适用路径：全新安装、带已有数据升级、停止后重启、换机恢复，以及包损坏/版本不兼容/工程仍运行等拒绝路径；更新器还需验证中断和失败后的恢复。数据验收覆盖账号、绑定、实例、文件引用及用户修改，不能只看健康接口或进程存活。

UE 验收联动 `ue-super-steward`：固定关卡绑定不会随网页切项目改变；至少验证对应实例实际加载。不能把本机新工程通过当成目标客户工程已通过。

交接说明：原版本→新版本、实际环境与 UE 工程、备份位置、迁移结果、数据保留证据、各组件验证状态和失败恢复方法。区分“已实现”“已测试”“待目标机验证”。建议建设顺序为固定环境与存储→可验证备份/恢复→协调更新入口与版本展示。
