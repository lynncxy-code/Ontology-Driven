## A · 删除 `ue5/` 死代码

### 目标
移除仓库根 `ue5/` 目录——它是 UE 插件的**旧副本，已停止维护**。

### 证据
- `ue_project/Plugins/OntoTwinSync/Source/OntoTwinSync/` 里有同名文件的**维护中版本**，且插件版还多出 3.5 的 `OntoTwinRuntimeGizmo` / `OntoTwinRuntimeEditorPanel`（ue5/ 里根本没有）。
- 插件 `README.md` 原文：「源码迁移自仓库根目录 `ue5/`（原文件保留作参考，**不再维护**）」。

### 涉及文件（整目录 8 个）
```
ue5/test0316.cpp / .h              （空壳模块声明）
ue5/TwinSceneManager.cpp / .h      （旧版，缺 3.4/3.5 能力）
ue5/TwinInstance.cpp / .h
ue5/DigitalTwinSyncComponent.cpp / .h
ue5/test0316.Build.cs
```

### 动手前必须核实（否则不删）
1. 全仓库 grep `ue5/`、`test0316` 的引用——确认没有**构建脚本 / 文档正文 / start 脚本**把 ue5/ 当作源。
2. 确认 `.gitignore` 没有把 ue_project 的对应源码排除（若排除了，ue5/ 可能是唯一进 git 的副本 → 不能删）。
   - 已知：CLAUDE.md 说「`ue_project/*` 整体 gitignore，仅追踪 `Plugins/` 源码」——即插件源码**在** git 里，ue5/ 确实是冗余。仍需实测确认。

### 验证
- 删后 `git status` 只显示 8 个 deletion；仓库其余文件的 grep 引用为 0。
- 不涉及后端/前端运行，无需起服务。

### 回滚
`git restore --staged --worktree ue5/` 或 `git revert`。git 历史永久保留，删了也随时能翻出来。

## B · 硬编码数据搬出源码

把两个「假体量」大文件里写死的数据搬进 `data/` 下的 JSON，代码改成启动时 `json.load` 到**同名变量**——下游 import 与用法**零改动**。

> 合规确认：CLAUDE.md 禁止改的是 `ProjectStore 文件格式 / mapping_rules.json / lite_* 表`。本项搬的是**代码里的常量**（`OBJECT_TYPES` / `MOCK_ASSETS` / demo 图），schema.sql 注释也明说这些「保持代码/git 配置、不入库」——搬成 JSON 仍是 git 配置，只是不再内联进 Python，**不触碰任何存储结构**。

### B1 · app.py 的 demo 语义图
- **现状**：`get_graph_data()`（约 3042–4260，~1200 行）里写死一整张 ECharts `{nodes, links, categories}`，注释自认「始终只返回内置 Demo 数据」。
- **改法**：抽成 `backend/data/demo_graph.json`；路由体改为读文件（可模块级加载一次缓存）。末尾那段「动态同步 injected_interfaces」的逻辑保留在 Python 里，只把静态数据外置。
- **注意**：中文内容多，读写强制 `encoding='utf-8'`。

### B2 · mapping_store 的类型表与 Mock 资产
- **现状**：`OBJECT_TYPES`（约 91–2256）+ `MOCK_ASSETS`（约 2257–2650）合计 ~2100 行字面量。
- **改法**：搬进 `backend/data/object_types.json` + `backend/data/mock_assets.json`；`mapping_store.py` 顶部 `OBJECT_TYPES = json.load(...)`，保持模块级变量名不变。
- **依赖面**：`from mapping_store import OBJECT_TYPES` 等 import 全部照常工作，因为变量名与 dict 结构不变。`INTERFACES` **暂不搬**（它是 D 项的单一声明源，且被 `build_ontology_json` import，先留在代码里）。

### 验证（B1+B2 通用）
1. 搬完写一次性断言脚本：`json.load` 回来的 dict 与搬走前的**快照逐键相等**（防止手抖漏条目 / 编码坏字）。
2. `docker compose up` 起后端，命中 `/api/v2/ontology/graph_data`、`/api/v2/ontology/types`、`/api/v2/assets`，返回体与改动前**字节级一致**（可先存一份 curl 输出做 diff）。
3. ECharts 不关心 key 顺序，`json.dumps` 时无需保序。

### 回滚
纯 git revert。JSON 与加载代码是一次提交，回退即恢复内联。

### 工作量
搬运机械但量大，主要耗时在「断言相等」这一步做扎实。半天。

## D · I3D 字段收口（缩水版）

### ⚠ 上次判断的修正
上次我把 `writeback.py` 的 `tx/ty` 算作「translation_x 的第 8 份手写副本、命名已漂移」——**错了**。核实 `writeback.py` 后确认：
- `tx/ty/tz` 是 **UE 上行 payload 的线格式契约**（docstring 第 41 行）。
- `translation_x` 是 **raw_state 的存储格式**。
- writeback 第 56–60 行做的正是两者之间的**翻译**，是刻意的边界适配器。
- 所以 `writeback._DEFAULTS`（tx 命名空间）**必须保留，不参与收口**。

### 收口的真实范围（仅 Nexus）
真正在重复「同一组 I3D 字段定义」的 Python 副本，缩到只剩：

| 副本 | 处理 |
| :-- | :-- |
| `mapping_store.INTERFACES` | **保留为唯一声明源**（已是权威，已被 build_ontology_json 消费） |
| `project_store._default_raw_state()` | 改为**从 INTERFACES 派生**默认值，不再手写字面量 |
| `ontology.py::SharedState` | 1.x 遗留，只服务 index.html 的 3 个 demo 实例——**评估直接退休**，而非收口 |

### 改法
在 `mapping_store`（或新建 `backend/i3d_defaults.py`）加一个 `default_raw_state_from_interfaces()`，遍历 `INTERFACES` 的 `properties[].default` 生成默认 dict；`_default_raw_state` 调它，再叠加它自己那套按类型的特例（airplane/agv/tooling 的 altitude/battery 等业务字段——这些**不属于** I3D，保留手写）。

### 明确不做
- **UE C++ 侧**（`TwinInstance.cpp` 那 30 行 `TryGetNumberField("translation_x")`）：跨语言代码生成，成本远高于收益，**本轮不碰**。字段名靠约定 + 后端契约稳定即可。
- **前端表单**：同理，不为收口去改 HTML。

### 风险
中。`_default_raw_state` 是新实例出生时的初值来源，改错会让所有新实例初值异常。必须有实例 spawn 的前后对比测试（新建一个实例，比对 raw_state 与改动前完全一致）。

### 建议
B 做完、app.py/mapping_store 瘦身后再评。若届时觉得「INTERFACES 与 _default_raw_state 手动同步」并没实际咬到你，D 可以不做——它是**防御性**收口，不是止血。

## 明确不做清单（避免过度工程化）

| 诱惑 | 为什么不做 |
| :-- | :-- |
| 把 app.py 拆成 Blueprint（域边界很干净：ontology 19 / coord 11 / binding 9…） | 87 路由现在跑得好好的；对单人开发，拆包收益主要是「看着舒服」，代价是全量 churn + 回归风险。**等 B 搬走 1200 行 demo 后 app.py 只剩 ~2500 行，痛感自然下降，届时再评**。 |
| 抽前端 `api.js` 统一 API 层 | 实测 8 页 71 处调用**几乎全是相对路径** `/api/v2/...`，跨环境本就通用，无 baseURL 重复问题——**伪需求**。 |
| 前端 10 页统一 `:root` token / UI 组件 | `ontotwin-ui` 规范自己定调「其他页面不为统一去重构」。顶多顺手去 emoji / 去原生 alert。 |
| 统一 99 处 `jsonify` 响应信封 | 会碰 87 处，churn 不小，收益中等。单人项目优先级低。 |
| 合并 coord_transform 前后端双份 | 刻意对称（前端要即时预览，后端要权威计算），不是重复。**该补的是一致性测试，不是抽象**。 |
| 给 ProjectStore 叠 Repository 层 | 现有继承方案已教科书级，别动。 |
