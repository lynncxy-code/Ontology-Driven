# OPT-06 UE 与后端同步方式改进建议

- 状态：方案已与产品确认（2026-11-22 至 11-23），尚未开发
- 依据：dev `d855cbf` 的代码，以及 5501 验收环境的只读实测
- 本文只写“做什么、为什么、怎么衡量”，不含实现代码

## 一句话结论

系统卡的主要原因不是 UE “隔一会儿问一次后端”，而是**后端每被问一次，就把整个项目从数据库重新读一遍**。所以分两步走：先让后端不再重复读取（只改后端，现场 UE 不用升级）；再把 UE 的几条询问合成一条，并改成“长轮询”（问一次，等到真有变化才回答）。不需要新增任何依赖，也不改变后端的运行方式。WebSocket 暂不做。

## 一、现在 UE 怎么和后端同步

每打开一个 UE 关卡，插件里有下面几条“定时询问”同时在跑：

| 问什么 | 多久问一次 | 拿回什么 |
|---|---|---|
| 物体数据（位置、状态、模型） | 0.5 秒（编辑模式 1.5 秒）；上一次没回来就跳过这一轮 | 只拿变化的部分（“增量”机制已存在且默认开启）；出错时退回拿全部 |
| 场景交互配置（漫游、解说） | 1 秒 | 每次拿整份配置 |
| 心跳（告诉后端“我还在”），顺带取回实时数据开关指令 | 2 秒 | 很小 |
| 网页交互配置 | 1 秒 | 带版本号，没变化就回“没变” |
| 有没有资产扫描任务 | 2 秒 | 很小 |
| 资产目录上报 | 60 秒 | — |
| 绑定状态检查 | 只在没绑定成功时 2～5 秒一次 | 很小 |

合计：**一个 UE 关卡什么都不做，每秒也要问后端约 5 次**。

另有一个旧的 1.x 同步组件（0.5 秒一次，旧接口），代码里已标为“旧版”，新场景不使用。

## 二、问题出在哪里

1. **每次询问都整份重读项目。** UE 的每条询问都带着“项目编号”。后端收到后，第一件事是把这个项目的全部物体、类型、分区从数据库读出来，再核对一次绑定关系。物体数据那条询问在处理时还会再读第二遍。
2. **读一遍有多贵（5501 只读实测）：** 最大的 ZHHZ 项目（674 个物体，近 2 万个零件）读一遍约 0.18 秒；SCC W18（322 个物体）约 0.03 秒。
3. **推算结果：** 一台 UE 连着 ZHHZ，后端每秒要花约 1.3 秒在重复读取上，还没算后面拼装数据的时间。也就是说，**连上两三台 UE，后端就开始排队**，画面更新会从 0.5 秒拖到一两秒甚至更久。这是按代码和单次实测推算的，没有做压力测试。
4. **“只给变化部分”的判断失效了。** 这套机制判断“有没有变”的依据是“这件东西还是不是内存里原来那件”。在项目常驻内存时这个依据可靠；4.8 改成每次询问都重新读一份后，每次都会被当成“全部可能变了”，于是每次都要把所有物体重新拼装、逐项比较。发给 UE 的结果仍然正确，也仍然很小，只是后端白算了。（这一条根据代码推断，未实测。）
5. **网络不是瓶颈。** 没有变化时，增量回答几乎是空的。只有在“整份重发”时数据才大，ZHHZ 一次整份重发估计超过 16MB。会触发整份重发的情况有：后端重启、某个物体的结构变了、UE 落后超过 128 批变化、同时在用的“项目＋分区”组合超过 32 个。

**现在的“实时”延迟上限：** 物体变化最晚约 0.5 秒，加上后端处理时间（大项目上本身就超过 1 秒）；交互配置最晚 1 秒；实时数据开关指令最晚 2 秒；资产扫描任务最晚 2 秒。

## 三、相关现状

- **后端运行方式：** 容器里直接运行 Flask 自带的简易服务器（`python app.py`，多线程模式）。每个连接占一个线程，没有上限。它能处理“慢一点再回答”的请求，但本身不支持 WebSocket。依赖清单里目前没有任何长连接相关的库。
- **已有的 WebSocket：** 只在 UE 一侧使用。UE 用自带的 WebSockets 模块，主动连接第三方的人流数据服务器（默认地址 `ws://10.191.12.40:8080/ws/targets`，默认关闭），带自动重连。数据优先级是：手动锁定 > 有心跳的 WebSocket > HTTP 快照。后端从头到尾不开 WebSocket：《外部数据监控台 WebSocket 监控与开关》里的开关，是借心跳把指令带给 UE，再借心跳把连接状态带回网页。插件里还有一条来自现场的警告：内网 WebSocket 可能被代理拦截。
- **网页里的定时询问：** `viewer.html` 每 0.5 秒拉一次全部数据，但没有其他页面链接到它，像是旧页面；项目列表页每 5 秒刷新一次；资产扫描期间有两处每 1.5～2.5 秒查一次进度。量都不大，不在本次范围内。

## 四、四种做法对比

| | 只优化轮询 | 长轮询 | 服务器推送（SSE） | WebSocket |
|---|---|---|---|---|
| 用户能感到的变化 | 不卡了，延迟仍有 0.5～1 秒 | 不卡，变化后约 0.1 秒可见，空闲时几乎没有请求 | 同长轮询 | 同长轮询；只有每秒推送十几次以上时才明显更好 |
| 要改哪里 | 只改后端 | 后端，加 UE 插件少量代码 | 后端，加 UE 端自己写一个数据流解析 | 后端，加 UE 端（可复用现有连接代码） |
| 新依赖或换运行方式 | 不需要 | 不需要 | 不需要 | **需要**：新增 Python 库，或更换后端运行方式 |
| 离线交付和 Docker | 无影响 | 无影响 | 工厂代理可能把数据攒着不发 | 新库要事先打进镜像；代理可能拦截 |
| UE 端难度 | 无 | 低：还是原来的请求，只是多等一会儿 | 高：UE 没有现成的接收方式 | 低：UE 自带，插件已有重连代码 |
| 出问题怎么退回 | 本身就是兜底 | 后端不等待、立刻回答，就和现在一模一样，自动退回 | 断开后退回定时询问 | 断开后退回定时询问，插件已有同类做法 |

关键点：**不管换哪种方式，都得先解决“每次整份重读”**。推送也要先知道“什么变了”，靠的正是第一阶段要做的版本号。

## 五、已确认的决定

1. 方向：先去掉重复读取，再改长轮询；WebSocket 暂不做。
2. 版本号只放在后端内存里，另外每 30 秒核对一次数据库作为兜底；**不改任何存储结构**。后端重启后版本号从头开始，UE 会收到一次整份重发，和现在重启时一样。
3. 第一阶段只改后端，现场 UE 不用升级；第二阶段把“合并询问”和“长轮询”一起做进 UE 插件，一次升级到位。旧接口保留，新旧插件可以同时在线。

## 六、分阶段做法

### 第一阶段：去掉重复读取（只改后端）

- 后端在内存里保留每个项目的数据和一个“版本号”。项目数据每改一次，版本号加一；版本号没变，询问就直接用内存里的数据，不再读数据库。
- 每 30 秒仍从数据库核对一次，用来发现绕过后端直接改库的情况（见第九节）。
- 修好“只给变化部分”的判断：改为依据版本号或内容本身判断，不再依据“是不是内存里原来那件”。
- 每次询问都要做的绑定核对也一并缓存，绑定关系变化时立刻作废缓存。
- 现有接口、返回格式一律不变，UE 插件不用动。

用户可感知的结果：多台 UE 同时连接大项目时不再排队、不再卡。

### 第二阶段：合并询问加长轮询（改 UE 插件和后端）

- 新增一条“有没有新事？”询问，一次带回物体数据、场景交互、网页交互、扫描任务各自的版本号；顺带完成心跳上报和实时数据开关指令的下发。
- 这条询问由后端最多“挂住”约 25 秒：期间任何一项有变化就立刻回答；一直没变化就到点回答“没变”，UE 马上再问。
- UE 只在某一项的版本号变了时，才去拿那一项的具体内容；物体数据继续沿用现有的增量接口。
- 物体数据、场景交互、网页交互、心跳、扫描任务原来各自的定时询问停掉。资产目录 60 秒上报一次和绑定检查保持不变。
- 后端保留全部旧接口，没升级插件的 UE 照常工作。

用户可感知的结果：变化约 0.1 秒内在 UE 里可见；一个 UE 关卡空闲时的请求从每秒约 5 次降到几十秒 1 次。

### 暂不做：WebSocket

等将来出现“后端需要每秒推送十几次以上”的需求再考虑。人流这类高频数据现在由 UE 直接连第三方服务器，不经过我们的后端。真要做时，需要先征得产品同意新增依赖，并验证工厂内网代理是否放行。

## 七、怎么衡量有没有变好

先测一组“改之前”的数字。测试用 5501 的数据副本另开临时环境进行，不对 5501 本身加压。每个阶段完成后，用同样的方法再测一次。

| 指标 | 怎么测 | 现在（推算） | 第一阶段目标 | 第二阶段目标 |
|---|---|---|---|---|
| 后端处理一次物体数据询问要多久 | 后端日志记录每次耗时 | ZHHZ 上 0.4 秒以上 | 0.05 秒以内 | 同左 |
| 一台 UE 空闲时，后端每秒收到几次请求 | 统计后端访问日志 | 约 5 次 | 不变（约 5 次） | 0.1 次以下 |
| 网页改一个物体，到 UE 画面变化要多久 | 对比后端保存时间和 UE 日志“增量已应用”的时间 | 0.5～2 秒 | 0.6 秒以内 | 绝大多数在 0.3 秒以内 |
| 同时连 1、2、4 台 UE（ZHHZ）时后端的 CPU 占用 | `docker stats` | 1 台即接近一个核满载 | 4 台合计明显低于一个核 | 同左或更低 |
| 整份重发的次数 | 统计后端返回的重发原因 | 未统计 | 只在重启或结构变化时出现 | 同左 |

## 八、出问题怎么退回

- **第一阶段：** 留一个开关，关闭后恢复为“每次询问都读数据库”的现有做法，不需要改代码、不动数据。版本号只在内存里，没有任何数据需要回滚。
- **第二阶段：** 后端不挂住询问、立刻回答，效果就和现在的定时询问一样；UE 插件在新询问连续失败时，自动退回原来的各条定时询问。旧接口一直保留，所以也可以直接让现场继续用旧插件。

## 九、给后续开发者的注意事项

- **所有写入口都必须让版本号加一**，否则 UE 会看不到改动。目前改项目数据的入口都在 `project_store.py` 和 `project_store_pg.py` 里（包括整份保存 `_save_current`、`transact_project`、`transact_expected_active`、`write_project`、回收站恢复、组件包保存，以及新近加入的运行时物体增删 `edit_runtime_objects`；预览批量回写也经由 `transact_project`）。新增写入口时要同步处理，并补测试覆盖。
- **绕过后端直接改库的只有 `01-source/backend/tools/` 下 3 个 ZHHZ 数据整理脚本**（`consolidate_zhhz_types.py`、`reclassify_zhhz_aircraft_paths.py`、`rollback_zhhz_round5_support_migration.py`），靠 30 秒核对来发现。若以后核对周期内的短暂延迟不可接受，再讨论别的办法。
- 后端账号模块里另有两处直接改项目表，只改项目属于哪个组织、哪个工厂，不影响 UE 看到的数据。
- 内存里每个项目缓存一份，要注意大项目的内存占用（ZHHZ 零件配置文本约 16MB），以及项目删除、移入回收站时及时清掉缓存。
- 版本号、缓存、长轮询都不写入数据库，不改 `ProjectStore` 的存储格式。如果开发中发现必须改存储结构，先停下来问产品。
- 第二阶段的“挂住等待”会让每台 UE 长期占用后端一个线程；按现有运行方式，几十台以内没有问题。上线前要按“最多多少台 UE 同时连接”验证一次。
