# OntoTwin 3.2.1 — 楼层空间高度配置补丁（PRD）

> 版本：3.2.1  
> 状态：已实施，待现场验收  
> 日期：2026-08-19  
> 关联基线：OntoTwin 3.1 三维坐标体系统一、OntoTwin 3.2 坐标体系前端交互优化、CAD 空间底图草稿与发布补丁  
> 适用页面：`frontend/coord_workbench.html`，并对 `frontend/instance.html` 做小范围说明补丁  
> 实施原则：单人维护、不过度工程化；前端遵循 `ontotwin-ui`

---

## 1. 背景

当前“③ 标定”顶部只维护底图名称、楼层编号和 UE 运行关卡。普通 CAD 构件的楼层 Z 则依赖项目空间剖面 `spatial_profile.floor_table` 中的 `z_base_mm`：

```text
默认构件 UE Z（cm）= 楼层 z_base_mm × scale_to_cm
```

项目默认 `scale_to_cm=0.1`，例如：

| 楼层 | `z_base_mm` | 默认构件 UE Z |
|---|---:|---:|
| 1F | 0 mm | 0 cm |
| 2F | 4500 mm | 450 cm |

后端已经能保存多层楼层表，但坐标标定工作台没有楼层高度维护入口。单层项目可以通过“1F + UE 地面 Z=0”绕开，多层项目则无法在正常页面内完成配置。

此外，图片标定能够从地面锚点得到 `ue_ground_z_cm`，普通 CAD 构件却使用 `z_base_mm` 派生 Z。两种高度语义不同，但当前界面没有解释，容易造成以下误解：

- 把 UE 运行关卡当成楼层高度配置；
- 以为图片地面锚点会改变普通 CAD 构件 Z；
- 在实例位置编辑中逐个修改 Z，替代项目级楼层配置；
- 直接调用通用空间剖面接口整体替换 `floor_table`。

本补丁补齐项目级楼层空间配置入口，并修正楼层基准变更后的全场重算语义。

---

## 2. 当前问题

### 2.1 产品问题

1. CAD 标定页只有“楼层”，没有“该楼层的规范标高”。
2. `z_base_mm` 和 `ue_ground_z_cm` 同属高度信息，但没有面向用户的区别说明。
3. CAD 模式只能标 XY，图片模式可以记录地面 Z，两个流程缺少共同的楼层配置视图。
4. UE 运行关卡与楼层放在同一行，容易被误认为能够设置 Z。
5. 新楼层缺少表项时，后端会回退到 0，可能让 2F 构件被静默放到 1F 高度。

### 2.2 正确性问题

当前空间剖面写入后会调用 `_rederive_components()`，但已有构件只在 `canonical_z` 为空时回填楼层基准。若构件已经保存了旧的 `canonical_z`，修改 `floor_table` 后不一定会随楼层整体移动。

当前新实例铸造也可能直接使用楼层基准 Z，而非构件已经派生出的 `ue_z`，从而丢失实例位置编辑产生的个别 Z 微调。

### 2.3 写入安全问题

通用接口 `PUT /api/v2/spatial/profile` 可以整体替换 `floor_table`，缺少面向楼层配置的字段校验、影响说明和单楼层更新语义。其“保存 profile → 重算构件 → 更新实例”也是多步写入，存在短暂不一致风险。

## 3. 产品决策

### 3.1 高度语义明确分离

| 名称 | 字段 | 单位 | 事实含义 | 主要消费者 |
|---|---|---:|---|---|
| 规范楼层标高 | `z_base_mm` | mm | 建筑规范坐标中该层的基准 Z | 普通 CAD 构件、绑定实例 |
| UE 实际地面 Z | `ue_ground_z_cm` | cm | UE 世界坐标中可行走地面的实际 Z | 人物路线、地面检测等 |
| UE 运行关卡 | `ue_level` | 路径 | 底图绑定的 UE 场景地图 | 场景匹配、发布校验 |

三者必须分开保存、分开说明：

- `z_base_mm` 决定普通 CAD 构件默认 Z；
- `ue_ground_z_cm` 不参与普通 CAD 构件默认 Z 计算；
- `ue_level` 不参与任何高度计算。

允许 `z_base_mm × scale_to_cm` 与 `ue_ground_z_cm` 不相等，以兼容 UE 世界原点偏移、地面模型厚度和行走面偏移。

### 3.2 楼层高度属于项目级配置

同一楼层的所有普通构件共用一个 `z_base_mm`。楼层配置在“③ 标定”就近维护，但数据仍属于项目空间剖面，不属于某一张 CAD 或图片底图。

实例运维中的 Z 只用于个别微调，不作为整层高度维护入口。

### 3.3 不修改现有项目存储格式

本补丁继续复用 `spatial_profile.floor_table` 的既有字段：

```jsonc
{
  "floor": 2,
  "floor_id": "floor-2",
  "z_base_mm": 4500.0,
  "ue_ground_z_cm": 470.0,
  "ue_level": "/Game/Maps/Main",
  "map_codes": []
}
```

不新增持久化的 `z_offset_mm`，不升级项目 schema，不改变 `ProjectStore` 文件格式。实例 Z 微调量在重算时由 `component.canonical_z - old_z_base_mm` 得到。

### 3.4 楼层配置与底图发布是独立动作

“保存楼层配置”使用独立按钮和接口；“保存标定草稿 / 发布空间底图”继续维护底图、锚点和变换。

底图发布不得静默创建一个高度为 0 的新楼层。当前底图选择了尚未配置的楼层时，应先引导用户保存楼层配置。

## 4. 目标

1. 用户可以在坐标标定工作台完成单层和多层的楼层高度配置。
2. 用户能清楚区分规范楼层标高、UE 实际地面 Z 和 UE 运行关卡。
3. 修改楼层基准后，本层普通构件和绑定实例整体移动，同时保留个别 Z 微调。
4. CAD 与图片模式共享同一份项目楼层配置。
5. 新楼层未配置时不再静默按 0 mm 发布或保存构件。
6. 楼层写入具备字段校验、项目一致性保护和原子更新。
7. 现有项目无需迁移即可继续使用。

---

## 5. 非目标

- 不新增楼层删除能力。
- 不引入独立空间配置页面、前端构建工具或异步任务队列。
- 不改变 XY 标定算法和锚点发布门槛。
- 不让 UE 运行关卡自动推断楼层高度。
- 不用 `ue_ground_z_cm` 替代普通构件的 `z_base_mm`。
- 不让自由实例随楼层表批量移动。
- 不重构实例运维页面的整体布局。
- 不修改现有页面路由。

## 6. 坐标与重算规则

### 6.1 新构件默认 Z

新保存的普通构件使用所属楼层基准：

```text
component.canonical_z = floor.z_base_mm
component.ue_z = component.canonical_z × scale_to_cm
```

### 6.2 个别实例 Z 微调

绑定构件的实例位置编辑仍写回构件 `canonical_z`。其相对楼层基准的微调为：

```text
z_offset_mm = component.canonical_z - floor.z_base_mm
```

该值只作为重算过程中的派生量，不新增存储字段。

### 6.3 楼层基准变更

楼层从 `old_base` 调整为 `new_base` 时，对属于该楼层的每个普通构件执行：

```text
old_offset = component.canonical_z - old_base
new_canonical_z = new_base + old_offset
new_ue_z = new_canonical_z × scale_to_cm
```

兼容规则：

- 旧构件缺少 `canonical_z`：视为旧基准，微调量为 0；
- 构件所属楼层在旧表中不存在：旧基准按 0 处理，同时返回数据告警；
- 自由实例没有绑定构件：不参与楼层批量移动；
- 只修改 `ue_ground_z_cm`：不重算普通构件和实例；
- 只修改 `ue_level`：不重算任何位置。

### 6.4 铸造实例

新铸造实例的 Z 应优先使用构件派生结果：

```text
translation_z = component.ue_z
```

若旧构件没有 `ue_z`，才回退到：

```text
translation_z = component.canonical_z × scale_to_cm
```

不得无条件回退到楼层基准，否则会丢失个别微调。

## 7. 前端设计

### 7.1 “③ 标定”顶部结构

原来的单行配置拆成三个视觉区域。

#### A. 底图信息

- 底图名称；
- 所属楼层；
- 当前项目已配置楼层的简要列表。

用户改变所属楼层后：

1. 从已加载的楼层表中查找该层；
2. 已存在则填充对应高度；
3. 不存在则显示“该楼层尚未配置”，规范楼层标高保持空值；
4. 用户有未保存的楼层编辑时，切换楼层前使用自定义模态提示保存、放弃或取消。

不得为 2F、3F 等新楼层自动填入 0 mm。

#### B. 楼层空间配置

字段：

- `规范楼层标高（mm）`：必填数值；
- `默认构件 UE Z（cm）`：只读，实时显示 `z_base_mm × scale_to_cm`；
- `UE 实际地面 Z（cm，可选）`：CAD 模式可手动输入；
- 楼层状态：已配置 / 未配置 / 有未保存修改；
- 操作：`保存楼层配置`。

常驻说明：

> 规范楼层标高决定本层普通构件的默认 Z。UE 实际地面 Z 只用于人物路线和地面检测，两者可以不同。

交互要求：

- 只有一个黑底主操作；
- 保存期间按钮禁用并显示“保存中”；
- 输入错误在字段附近展示，不使用原生 `alert()`；
- `z_base_mm` 发生变化时，用 `UI.modal` 说明本层构件和绑定实例会重新计算；
- 只修改 UE 实际地面 Z 时，不显示构件重算警告；
- 保存成功后编辑区继续可用，并在成功横幅中提供一次“撤销本次修改”；
- 失败使用 `UI.toast`，409 明确提示“当前项目已切换，请重新加载”。

#### C. UE 场景绑定

把 `UE 运行关卡` 移到独立区域，文案改为：

> 绑定的 UE 场景地图（可选）

常驻说明：

> 运行关卡只用于场景匹配，不会设置楼层高度或构件 Z。

该字段继续随底图草稿和发布保存，不与楼层高度保存按钮混为一个动作。

### 7.2 CAD 模式

- 用户可以手动维护当前楼层的 `z_base_mm`；
- 用户可以选填 `ue_ground_z_cm`；
- CAD 锚点继续只填写 UE X/Y，不扩展为三维锚点；
- 当前楼层未配置 `z_base_mm` 时，不允许发布空间底图或保存该层构件；
- `ue_ground_z_cm` 为空不阻断 CAD 空间底图发布，但需要地面能力时由对应页面提示补齐。

### 7.3 图片模式

- 显示与 CAD 相同的楼层空间配置卡片；
- `z_base_mm` 仍由用户在项目级楼层配置中维护；
- `ue_ground_z_cm` 由用户选定的地面锚点 UE Z 自动得到；
- 图片模式中该字段显示为只读，并标注“来自锚点 <名称/编号>”；
- 需要修改时，引导用户重新选择地面锚点；
- 发布准备覆盖该楼层已有的手工地面 Z 时，模态展示旧值和新值；
- 图片发布只更新 `ue_ground_z_cm` 和既有底图元数据，不覆盖 `z_base_mm`。

### 7.4 实例位置编辑

`frontend/instance.html` 只做低风险说明增强：

- 显示当前楼层基准，例如“2F 基准：4500 mm / 450 cm”；
- 将 Z 编辑说明为“当前实例的个别微调”；
- 切换楼层后回到新楼层基准，微调归零；
- 明确“修改这里只影响当前实例；整层高度请回到坐标标定工作台设置”。

不重写现有多坐标联动面板。

## 8. 接口设计

### 8.1 查询楼层配置

```http
GET /api/v2/spatial/floors
```

响应示例：

```jsonc
{
  "project_id": "project-scc-w18",
  "scale_to_cm": 0.1,
  "floors": [
    {
      "floor": 1,
      "floor_id": "floor-1",
      "z_base_mm": 0.0,
      "default_component_ue_z_cm": 0.0,
      "ue_ground_z_cm": 20.0,
      "ue_level": "/Game/Maps/Main",
      "usage": {
        "components": 120,
        "bound_instances": 86,
        "frames": 2
      }
    }
  ]
}
```

`usage` 只用于保存前的影响说明，不作为新的项目持久化字段。

### 8.2 新建或更新单个楼层

```http
PUT /api/v2/spatial/floors/{floor}
Content-Type: application/json
```

请求示例：

```jsonc
{
  "expected_project_id": "project-scc-w18",
  "z_base_mm": 4500.0,
  "ue_ground_z_cm": 470.0
}
```

语义：

- `z_base_mm` 必填；
- `ue_ground_z_cm` 可为有限数值或 `null`；
- 只更新目标楼层的高度字段；
- 已有条目的 `floor_id`、`ue_level`、`map_codes` 和未知兼容字段保持不变；
- 新楼层自动生成 `floor_id=floor-{floor}`，`map_codes=[]`；
- 不接受通过该接口删除或重编号楼层。

响应示例：

```jsonc
{
  "status": "ok",
  "project_id": "project-scc-w18",
  "floor": {
    "floor": 2,
    "floor_id": "floor-2",
    "z_base_mm": 4500.0,
    "default_component_ue_z_cm": 450.0,
    "ue_ground_z_cm": 470.0
  },
  "changed": {
    "z_base_mm": true,
    "ue_ground_z_cm": false
  },
  "affected": {
    "components": 34,
    "bound_instances": 29
  },
  "warnings": []
}
```

### 8.3 校验与错误

| 条件 | 状态码 | 说明 |
|---|---:|---|
| 当前无激活项目 | 400 | 明确返回当前无激活项目 |
| 楼层不是 1～10000 的整数 | 400 | 字段错误 |
| 高度不是有限数值 | 400 | 拒绝 NaN、Infinity、布尔值和空字符串 |
| `floor` 或 `floor_id` 重复冲突 | 409 | 不静默合并两层 |
| 激活项目与 `expected_project_id` 不符 | 409 | 不得写入后来切换的项目 |
| 保存或重算失败 | 500 | 整个事务回滚 |

### 8.4 旧接口兼容

保留 `GET/PUT /api/v2/spatial/profile`。当旧 PUT 包含 `floor_table` 时：

1. 必须复用同一套楼层校验；
2. 必须复用同一套 Z 重算算法；
3. 不得继续直接替换后再分步重算；
4. 返回兼容响应，同时标记该写法为旧入口。

只修改 `ue_transform.display` 时不触发全场坐标重算；修改规范原点或实际坐标矩阵时才执行对应的 XY 重派生。

## 9. 后端实现设计

### 9.1 独立服务模块

新增：

```text
backend/floor_profile_service.py
```

负责：

- 楼层表读取和标准化；
- 单楼层字段校验；
- 楼层使用量统计；
- `z_base_mm` 变更影响规划；
- 构件 `canonical_z/ue_z` 重算；
- 已绑定实例 `raw_state.translation_z` 同步；
- 返回前端需要的影响摘要。

`backend/app.py` 只保留薄路由和错误映射，不继续放大业务逻辑。

### 9.2 原子写入

楼层条目、构件和实例必须在一次 `ProjectStore.transact_expected_active()` 中修改并落盘：

```text
读取 working 旧楼层
→ 计算每个构件旧微调量
→ 更新 working.floor_table
→ 重算 working.components
→ 同步 working.instances.raw_state.translation_z
→ 一次保存
```

任何一步抛错时，空间剖面、构件和实例都回滚到旧状态。

### 9.3 当前楼层事实来源

项目空间剖面是楼层高度的当前事实来源。图片帧中的 `floor_reference.canonical_z_base_mm` 和 `ue_ground_z_cm` 视为标定时快照/来源记录，业务接口不得把过期快照当成当前楼层配置。

空间底图响应或人物路线前端需要显示当前高度时，应按 `floor_id/floor` 从实时 `floor_table` 解析；必要时在响应中增加非持久化的 `resolved_floor_reference`。

### 9.4 底图发布约束

- CAD 发布前检查目标楼层已存在且 `z_base_mm` 合法；
- CAD 发布不更新 `z_base_mm` 和 `ue_ground_z_cm`；
- 图片发布前检查目标楼层已存在；
- 图片发布可以从地面锚点更新 `ue_ground_z_cm`，但不能覆盖 `z_base_mm`；
- 发布新楼层时不得再自动创建 `z_base_mm=0` 的楼层表项。

## 10. 数据兼容

### 10.1 现有项目

- 默认 1F 已有 `z_base_mm=0`，无需迁移；
- 已有多层表继续原样读取；
- 旧条目缺少 `ue_ground_z_cm` 时按 `null` 展示；
- 已有未知字段完整保留；
- 不修改 `schema_version`。

### 10.2 异常旧数据

- 构件引用了楼层，但楼层表不存在：在楼层列表中显示“未配置楼层 N”，不自动创建；
- 构件缺少 `canonical_z`：首次合法楼层重算时按旧楼层基准回填；
- 同一表中存在重复楼层或重复 `floor_id`：禁止写入并返回冲突明细，避免猜测合并；
- 自由实例继续使用自身绝对 UE 坐标，不参加修复性迁移。

## 12. 实施顺序

### P0 — 正确性修复

1. 提取楼层配置服务和校验函数；
2. 实现按旧基准保留个别微调的重算算法；
3. 使用单事务更新 profile、components 和 instances；
4. 修正新实例铸造丢失构件 Z 微调的问题；

## 14. 验收标准

1. 1F 配置 `z_base_mm=0` 后，普通构件默认 UE Z 为 0 cm。
2. 2F 配置 `z_base_mm=4500` 后，普通构件默认 UE Z 为 450 cm。
3. 2F 构件原有 `+25 mm` 个别微调时，楼层基准改变后仍保留该微调。
4. 楼层基准保存成功后，本层已绑定实例在下一轮快照中使用新 Z。
5. 只修改 `ue_ground_z_cm` 时，普通 CAD 构件和实例 Z 完全不变。
6. 修改 UE 运行关卡时，所有坐标完全不变。
7. 图片地面锚点可以更新公共地面 Z，且不会覆盖 `z_base_mm`。
8. CAD 与图片模式查看同一楼层时，显示同一份项目级配置。
9. 未配置的新楼层不能发布空间底图或保存构件，并显示就近引导。
10. 实例位置编辑明确属于个别微调，切楼层时回到新层基准。
11. 项目切换冲突不会写错项目。
12. 新铸造实例能够继承构件的个别 Z 微调。
13. 现有项目无需迁移即可打开、编辑和保存。
14. 完整流程“上传 → 配置楼层 → 标定 → 发布 → 保存构件 → 绑定铸造 → UE 同步”通过。

## 15. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 楼层基准修改导致大量实例瞬移 | 保存前展示影响范围；使用模态确认；成功后提供一次撤销 |
| 个别 Z 微调在整层重算后丢失 | 按旧基准计算偏移，再叠加到新基准；增加专门回归测试 |
| 通用 profile PUT 绕过校验 | 旧入口强制复用统一服务，不保留第二套重算逻辑 |
| 图片帧快照与实时楼层表不一致 | 消费端以实时 `floor_table` 为准，帧值只作标定来源记录 |
| 新楼层默认为 0 造成错层 | 新楼层保持“未配置”，发布和保存构件前强校验 |
| 写入过程中项目被切换 | 所有楼层写入携带 `expected_project_id`，在事务锁内检查 |
| UI 概念过多 | 三个独立区域、常驻白话说明、默认 UE Z 只读换算 |
