01 · 命题

它到底在解决什么问题

项目自己的产品说明书把根本命题写成一句话：画出来的形状 ≠ 业务上的身份。

一张工厂 CAD 图能告诉你「这里有个溶铜槽」，但说不出「这是溶铜槽 DW-007、挂着哪几个传感器、现在是不是在线」。绝大多数数字孪生项目栽在这一步：模型是美术手搭的，业务数据是另一套系统的，两边靠人肉对表。

OntoTwin 的做法是把「形状」和「身份」拆开，各自有独立的生产链路，最后在一个明确的工位上焊接。这条四段流水线是整个 Nexus 主线的脊梁：

本体层
类型 有哪些种类、彼此什么关系。ObjectType + 能力接口 + 属性。 语义图谱 / 本体配置中心
CAD 解析层
构件 图纸里哪里有个什么形状。有几何有坐标，没有身份编号。 坐标标定工作台
绑定层
实例 这个构件是谁。构件 + 业务编号铸造成实例——实例唯一的出生地。 实例绑定台
运行层
状态 实例此刻怎么样。只有铸造过的实例有资格被监控、被 UE 渲染。 实例运维 / UE5 / 推流

这条链路解释了仓库里几乎所有看似零散的模块：DXF 解析器、仿射标定、CSV 对账、UE 插件轮询——它们都是这四格里的某一格。

02 · 全景

一个仓库，两条主线

这是理解本仓库最重要的一件事：两条业务线共用同一个 Flask 进程和同一台端口，但存储、API 前缀、前端路径三重隔离，靠约定（ADR-012 / ADR-017）而不是靠代码强制。

主线 A · 占仓库 ~85%

OntoTwin Nexus — 工业数字孪生平台

把工厂楼层变成可监控的三维孪生。演进到 3.6，是这个仓库真正的主体。

  • API：/api/v2/...
  • 存储：PostgreSQL（运行层）+ Neo4j（语义层）
  • 前端：/nexus 入口 + 6 个功能页
  • 消费端：UE5 插件 OntoTwinSync
主线 B · 占仓库 ~15%

具身智能平台（lite）— USD 训练场景导出

复用本体数据，导出 Isaac Sim 可加载的 USD 场景，交付给训练侧同事。停在 M1 前后。

  • API：/api/v3/lite/...
  • 存储：独立 SQLite，全表 lite_ 前缀
  • 前端：/scenes
  • 消费端：Isaac Sim / Isaac Lab

两条线唯一的物理接触点是 app.py 结尾那段 try: register_lite_routes(app)——包在 try/except 里，lite 挂载失败也不影响主线启动。项目的协作约定甚至要求：开工前先确认在哪条线，选 Nexus 时完全不提 lite。

03 · 核心

Nexus 的四个关键内核

抛开路由数量和页面数量，这套系统真正的技术资产集中在四处。它们也是改动风险最高的四处。

内核一 · ProjectStore：单一事实来源 + 唯一可见性规则

一个 Project = 一个工厂/楼层的全部自洽数据（类型表 + 构件 + 实例清单 + 实例 + 标定）。内存中只保留当前激活项目一份——这条「唯一可见性规则」贯穿前端、UE、投产全链路，是根治「重启丢数据 / 实例串台」的关键设计。

3.4 做了一次漂亮的换底：ProjectStorePG 直接继承 ProjectStore，只覆盖读写落盘这几个 IO 原语，所有内存业务逻辑原样复用，对外方法签名完全一致——app.py 里 80 多处调用一行没改，靠环境变量 ONTOTWIN_STORE=pg 切换。这是全仓库最值得学的一处工程决策。

内核二 · 双真源分工：语义归图库，运行归关系库

层真源存什么写入通道
语义层（本体）Neo4jObjectType / InterfaceType / SharedPropertyType 及其继承、实现、要求关系只读运行时；写入必须走 本体 JSON → generate_ontology_cypher → cypher-shell
运行层PostgreSQLproject / object_type / instance / zone 四张表，嵌套块用 JSONB业务 API 直写，全面软删（deleted_at）
类型绑定PG（缓存）asset_id / ue_asset_path / color 等绑定字段语义字段由 sync_types_from_graph 从图库单向刷新，绝不反向写图

这个分工把「本体长什么样」和「现场有多少台设备」彻底解耦。图库不可达时相关接口降级 503，主功能不受影响——降级路径是显式设计过的。

内核三 · 坐标体系：三套坐标系之间的可逆变换

CAD 系
DXF 原始坐标。parser_dxf 扫 INSERT 块 → 候选类型；coord_filter_rules 按图层/块黑名单过滤。
规范系
米（内部 mm）· Z-up · 右手系，ADR-003 定死。coord_transform 用 numpy 最小二乘从 4 个锚点求 2D 仿射矩阵，带 RMSE 校验。
UE 系
厘米 · 左手系。转换规则：规范 × 100 = cm，Y 轴取反。前端 coord_transform.js 与后端算法对称实现。

难点在回写方向。writeback.py 按实例来源分类落点：绑定 CAD 构件的实例要把 UE 的 cm 逆变换回规范系写进构件的 canonical_*（否则会被后续重算覆盖掉）；自由实例的 raw_state 本身就是真源，直接写。这个模块刻意做成传输中立——不 import Flask，谁调都行。

内核四 · UE5 消费侧：从「固化」转向纯数据库驱动

ATwinSceneManager（1649 行，全仓库最大的 C++ 文件）是 UE 端唯一需要手放的 Actor：轮询 /api/v2/state/snapshots，按分区 spawn / 驱动 / despawn 所有孪生实例。3.4 明确废弃了「快照固化到关卡」——不再把衍生 Actor 烘进 .umap，改为全量 DB 驱动，同时打通 UE→后端回写与历史 Actor 的一次性收编（按 ActorGuid 幂等）。

3.5 在打包后的 exe 里加了 Runtime Editor：射线选中实例、gizmo 平面拖拽与 Yaw 旋转、靠墙吸附，保存即写回后端目标状态，编辑期用 bLocalOverrideLock 挡住轮询覆盖。3.6 再往前一步，用 Pixel Streaming 把 UE 画面 iframe 嵌进 Web 监控页——目前是本机 spike，标注为「开发完成，待关闭 VPN 后手动验收」。

04 · 第二线

具身智能平台：本体 → USD → Isaac Sim

目标很具体：让训练场景「数据驱动」而不是美术手搭。在 Nexus 前端配好场景（放哪些物体、在哪、可不可抓），一键导出 .usda，训练同事直接在 Isaac Sim 里加载。第一版任务是「按尺寸分拣箱子」：1 台 Franka 机械臂 + 3 个存放区 + 6–8 个箱子。

这条线的决策密度很高，19 条 ADR 几乎全在划边界。最关键的几条：

ADR决策为什么
001导出单向，不做 USD → Nexus 回流一人开发，双向映射工作量大收益低；留 customData 口子
002USD 只含静态场景，无 TimeSamples动态行为与训练无关，机器人自己就是动态源
006物理三分法：static / dynamic / graspablegraspable 必须 mesh 精确碰撞，不能用 convex hull
011每个 Prim 携带 customData.ontology 溯源块USD 落到训练侧后仍能追回是哪个实例、哪个本体类型
012独立 SQLite，不合并进现有存储隔离便于维护——也正是两条线不打架的根基
013/014不引入任务队列；不做权限/版本/审计一人用，10 物体级场景同步跑几秒就完

实现侧目前是 4 个 API 模块（assets / instances / scenes / export）+ usd_exporter（170 行，用 pxr 直接写 UsdPhysics schema）+ 一个不用 pytest、直接 python 跑的冒烟测试。assets/usd_cache/ 里已经躺着货架、纸箱、Franka、GR1T2 人形机器人等一批转好的资产。

06 · 演进

版本轴：从演示到真源

30 份 PRD 排成的时间轴，能看出一条很清晰的重心迁移：先证明能同步 → 再把语义建起来 → 再把坐标做对 → 最后把存储收成真源，并把交互推回 UE 运行时。

1.0 – 2.1三维语义接口与 DigitalTwinSync定义 I3D_Representable 能力接口体系；UE 组件轮询后端状态驱动单个 Actor。
2.2 – 2.8资产中台、数据集管理、场景构建插件ArtStudio 资产接入、数据集 CRUD、TwinSceneBuilder / PCBWorkerSync / AGVPatrol 等专项组件。
2.9.x坐标标定工作台（关键转折）DXF 解析 + 4 点仿射标定 + 图层选择性纳入 + CAD 实体批量入实例库。系统第一次能吃真实图纸。
3.0 – 3.0.2本体与 CAD 分层重构确立类型 → 构件 → 实例三层，新增实例绑定台。实例从此只有一个出生地。
3.1 – 3.3.1三维坐标体系统一 + 运行时模型加载规范系定死 m/Z-up/右手；后端预取 glb 落盘，绕开 UE HTTP 的代理与并发坑。
3.4数据库真源化（架构上最大的一次）JSON → PostgreSQL；语义层拆到 Neo4j；引入 zone 分区路由；废弃「固化到关卡」；历史 UE Actor 一次性收编。
3.5Runtime Editor MVP打包 exe 内选中实例、gizmo 编辑、写回后端目标状态。编辑权交回三维现场。
3.6Pixel Streaming 本机推流 SpikeUE 画面嵌进 Web 监控页。当前状态：开发完成，待手动验收。
07 · 观察

值得注意的地方

以下是从代码与文档比对中读出来的，按影响面排序。项目定位是单人开发、明确拒绝过度工程化，因此判断标准不是「不够企业级」，而是「会不会咬到自己」。

高文档与实现已经漂移

产品说明书（3.0 版）第 5、6 节仍写着「数据落在 backend/data/projects/，一项目一文件」「不加关系型数据库」——而 3.4 之后真源已是 PostgreSQL + Neo4j，backend/data/ 目录在当前工作区根本不存在。CLAUDE.md 的架构大图同样只描述了 JSON 版 ProjectStore，没提 PG / Neo4j / zone / writeback。

影响：这是喂给 AI 协作者和未来的自己的第一份上下文，错的上下文会持续产生错的改动方案。这一项修复成本最低、收益最高。

中两套存储实现长期并存，漂移风险已经埋下

ProjectStore（JSON）与 ProjectStorePG 靠继承共享内存逻辑，设计是干净的；但只要 JSON 版仍是默认（ONTOTWIN_STORE 不设时走 JSON），任何只在一侧验证过的改动都可能只在一个后端上正确。而且没有任何测试覆盖这两条路径的等价性。

建议：要么明确宣告 PG 为唯一支持路径、JSON 降级为一次性迁移工具；要么补一个跑两遍的最小等价性检查。

中核心数学逻辑没有任何自动化测试

全仓库唯一的测试是 lite 那条线的 USD 导出冒烟脚本（不用 pytest，直接 run）。而 coord_transform 的仿射求解、writeback 的逆变换分类落点，恰恰是「错了不会崩、只会悄悄偏几米」的那类代码——目前完全靠人眼在工作台里看 RMSE。

建议：即使不引入 pytest，也值得像 lite 那样写一个直接 run 的 test_coord_roundtrip.py，断言「规范系 → UE → 逆变换回规范系」误差在阈值内。这是投入产出比最高的一处测试。

中app.py 的膨胀有一半是假的，但另一半是真的

3772 行里约 1200 行是 get_graph_data() 里写死的 demo 语义图，注释明说「始终只返回内置 Demo 数据」；mapping_store.py 2855 行里也有 2100 行是硬编码类型表与 MOCK_ASSETS。把这两坨挪进 JSON 数据文件，两个「巨型文件」立刻回到可读区间。

剩下的一半是真的：87 条路由确实都挂在同一个模块里，坐标、绑定、资产、数据集、UE 同步全混在一起。项目自己的规矩已经写明「新功能放独立子目录，不要继续往 app.py 里塞」——lite 那条线证明了这条规矩可行。

低git 历史只有一个提交

整个仓库压成了单个 commit，没有任何演进痕迹。对单人项目影响有限，但一旦某次改动引入回归，将没有 git bisect 可用，只能靠 30 份 PRD 反推当时的意图。

低已知的功能性边界（项目文档自己承认的）

图片标定模式仍直接产实例，未迁移到「构件 → 绑定」链路，与 CAD 绑定混用同一项目会出问题；自动撮合只做 EQUIP_ID 精确匹配；UE 插件的 SetActorLabel 未包 WITH_EDITOR，打包发行版会编译失败；轮询是 0.5s HTTP 短轮询，无推送。

08 · 结论

一句话评价与下一步

这是一个想清楚了才动手的项目。「形状 ≠ 身份」的命题、类型/构件/实例的三层拆分、语义与运行双真源的分工、存储换底时用继承保住 80 处调用点——这些都不是随手写出来的东西，30 份 PRD 和 19 条 ADR 是真的在约束实现，而不是写完就扔。

它的风险不在架构，在知识的保存方式：设计意图全在文档里、历史全在 PRD 里、正确性全在人眼里。文档一旦落后于代码（现在已经落后了），这三样会同时失效。

如果只做三件事，我会选：

第一优先

把 CLAUDE.md / 产品说明书刷到 3.6

补上 PG + Neo4j 双真源、zone 分区、writeback、Runtime Editor；删掉已失效的「数据落在 data/projects」「不加关系型数据库」。半小时的事，止住持续性的误导。

第二优先

给坐标链路补一个 round-trip 断言

照 lite 冒烟测试的形式写，不引框架。护住整个系统唯一「错了不报错」的地方。

第三优先

把两坨硬编码数据搬出源码

demo 语义图与 OBJECT_TYPES 挪成 JSON 资源文件。零风险，直接让两个最大的文件回到可维护尺寸。
