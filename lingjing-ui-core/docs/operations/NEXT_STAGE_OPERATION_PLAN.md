## 2. 运行模式定义：默认模式 vs 非默认模式

> 目的：让后续“做什么/不做什么”不再凭感觉，而是有明确的默认列表与触发式列表。

### 2.1 默认模式：Observation 驱动运行（Always-on）

**默认模式** 是当前阶段在没有额外触发的情况下，AI/CodeBuddy 应持续执行的动作链，包括：

- **新样本 observation 记录**
  - 对每次实际任务（真实需求或重要模拟）记录：scene、page_type、选用模板、命中/误用情况、Guard 状态、用户反馈等。
  - 输出到统一的 observation log（可以按周期分段）。

- **周期整理与小结**
  - 按既定 observation 周期（例如每 N 个样本或每自然周），对本周期样本做整理：
    - 统计模板命中分布；
    - 汇总误用/回退案例；
    - 标记明显的新模式或新痛点。

- **模式聚类（pattern clustering）**
  - 基于样本，将类似场景/结构聚成模式簇，例如：
    - 新出现的“轻量助手 + 小工作台”形态；
    - 不同类型 dashboard 的信息架构差异；
    - 新的 cross-scene 混合模式。
  - 为后续 canonical 评估与模板升级提供数据支持。

- **轻量回填与文档补注**
  - 在不改变 router/matrix/模板结构的前提下，进行轻量回填：
    - 给已有模板增加/优化注释、aria、usage hints；
    - 在审查文档中补充新的 observation 发现（例如添加“常见误用样例”小节）。
  - 前提：不触及结构、不改变资产层级，只做说明增强。

- **候选池维护（见第 3 节）**
  - 对新的需求/痛点/机会点：
    - 不直接立刻执行结构性改动；
    - 而是录入到候选池，附上来源样本与初步思路。

- **阶段进度与状态汇报（见第 6 节）**
  - 每个 observation 周期结束时，按固定模板输出一次运行期报告：
    - 当前阶段、进度百分比；
    - 是否触发任何升级动作；
    - 候选池状态变化。

### 2.2 非默认模式：触发式治理动作（By-trigger only）

**非默认模式** 是只有在满足明确触发条件时才会启动的动作，包括但不限于：

- **Guard patch / Guard 规则增强**
  - 仅当 observation 显示某类误用频繁穿透现有 Guard、或 Guard 误杀率偏高时，才提出 patch 建议。

- **router / coverage / template 路由调整建议**
  - 仅当出现稳定的 coverage gap 或新模式胜出时，才讨论：
    - template_router/scene_coverage 的路由优化；
    - 为现有模板增加/修改路由标签。

- **第二批模板修复轮**
  - 仅当某些模板在修复后仍出现明显误用、或新模板暴露出高风险模式时，才考虑立项第二批修复。

- **局部 Phase 2 试点**
  - 仅当某 scene 或 cross-scene 模式在 observation 中表现稳定且价值显著时，才考虑：
    - 在该局部进入更深一层的结构/模板族治理（Phase 2 局部试点）。

- **新 scene 治理线 / 大规模规范建设**
  - 当前阶段默认不启动；若未来出现强需求，也必须由明确触发条件支撑（见第 5 节）。

## 3. 候选池（Candidate Pool）

> 候选池 = 下一步可以做、但当前不立刻做的方向清单。进入候选池 **不代表已经立项**。

### 3.1 候选池定义与使用原则

- **定义**：
  - 将 observation 中发现的潜在优化方向，统一收纳到一个结构化列表中，包含：
    - `类型`（模板/路由/scene/基础设施等）；
    - `简要描述`；
    - `来源样本/证据`；
    - `当前状态`（候选中 / 等待更多样本 / 建议冻结等）。
- **原则**：
  - 默认先入候选池，不直接变成执行任务；
  - 仅当触发条件矩阵（第 5 节）中某条被满足时，才从候选池中挑选并立项；
  - 若长期没有足够证据支撑，可在周期复盘中将候选项标记为“冻结/放弃”。

### 3.2 当前候选池起始清单（示例）

> 以下是基于当前治理过程已经显现、但明确不应立即启动的几个方向，作为候选池起始内容。后续可在 observation 运行中增删。

- **A. 局部模板 / 路由候选**
  - **`b-system-production-plan.html` 深度清理候选**
    - 方向：进一步澄清 planning/workspace vs advanced_list/list-edit 的边界，减少“把任何计划类页面都当 production-plan 壳”的误用。
    - 状态：候选中，等待更多与 planning 场景相关的 observation 样本。
  - **dashboard analytics 路由细化候选**
    - 方向：对高维度 analytics dashboard 细分 page_type 或路由条件，使其与简单 KPI 看板区分更清晰。
    - 状态：候选中，等待跨 scene 的 dashboard 模式聚类结果。

- **B. scene 深化候选**
  - **website 局部 Phase 2 候选**
    - 方向：在已有 website baseline 上，对高价值深度页型（如产品详情、解决方案页）进行更精细的 UX→UI 对齐与模板族设计。
    - 状态：候选中，需更多来自真实 website 任务的样本。
  - **presentation deck 族 canonical 评估候选**
    - 方向：在 `presentation-business` 初步修复基础上，联合 `presentation-product` / `presentation-planning` 等，评估 deck 族的样式统一与 canonical 候选。
    - 状态：候选中，等待更多关于 business/product/planning deck 使用情况的 observation。

- **C. 基础设施候选**
  - **UX → UI 闭环示范文档**
    - 方向：选取 1–2 个代表性 scene（如 ai_assistant workspace、某类 dashboard），编写“从 UX spec 到 UI 模板”的闭环示范说明书，帮助后续模板设计保持一致性。
    - 状态：候选中，优先级依赖后续 observation 中对“规格不对齐”问题的频次。
  - **Observation pattern cookbook**
    - 方向：将高频出现的 UI/UX pattern 抽取成 cookbook，作为 AI 生成和人工设计的参考资产。
    - 状态：候选中，适合作为运行期中后段的知识沉淀产物。

- **D. 暂缓项（明确暂不立项，仅挂名）**
  - **第二批模板修复轮**
  - **全面模板族治理（全库级）**
  - **新 scene 治理线**
  - **全面 Phase 2 启动**

> 上述所有条目目前都应视为“候选池内容”，而不是“已规划项目”。是否转为正式任务，完全取决于第 5 节触发条件矩阵。

## 4. 触发条件矩阵（Trigger Matrix）

> 目的：将“什么时候升级动作”显性化，避免凭直觉扩张治理范围。

### 4.1 触发条件总览

| 触发 ID | 观察信号（Evidence） | 建议阈值 | 触发后可启动的动作 |
|---------|------------------------|----------|---------------------|
| **A** 模板误用反复出现 | 同一模板在相似模式下被误用 ≥ 3 次，跨 ≥ 2 个 observation 周期；Guard 提示/人工回退记录中多次出现同一原因 | N≥3 且跨周期 | 立项 **局部模板修复轮** 或将该模板/族加入下一批修复候选，优先处理边界表达与 demo 噪音 |
| **B** 某 candidate 模式稳定胜出 | 某一模板或 UI 模式在多个可选方案中连续 2+ 周期被选为主方案，且误用/投诉极少 | 连续 2–3 个周期 | 启动 **canonical 评估** 或模板升级讨论，可考虑提升资产层级或调整 router 权重 |
| **C** coverage gap 持续存在 | 某类真实任务频繁出现“无合适模板”，或多次依赖临时拼接/临时 HTML 解决 | 至少 2 个以上独立任务样本 | 立项 **路由/模板扩展候选**：补模板、补路由或调整 scene coverage |
| **D** Guard 压力连续出现 | 同一 Guard 规则方向上，拒绝/误杀/绕过频次在连续周期中偏高，且来自不同任务样本 | 连续 2 个周期出现 Guard 压力 | 启动 **Guard patch 分析**：定位规则问题，提出精确 patch 建议 |
| **E** 跨 scene 混合模式积累 | 某类跨 scene 混合模式（如 digital twin + 运控、assistant + workspace）在 observation 中多次自然出现且效果良好 | 3+ 高质量样本 | 考虑启动 **局部 Phase 2 试点**：围绕该混合模式做深入建模与模板族设计 |

### 4.2 触发流程说明

- **第一步：Observation 记录与标记**
  - 在日常 observation 中，对可能涉及触发信号的样本做标记（例如“疑似覆盖缺口”“Guard 压力”“candidate 胜出”等）。
- **第二步：周期性阈值检验**
  - 在每个 observation 周期的小结中，检查各触发 ID 的条件是否被满足：
    - 若未满足，保持现状，仅在候选池中更新对应条目的“证据数”；
    - 若满足，则将对应候选项升级为“建议立项”，并在运行期报告中显性列出。
- **第三步：决策与排期（可由人工 + AI 共决）**
  - 当某触发被满足时，由人/AI 根据实际资源评估是否：
    - 立即立项进入下一周期；
    - 延后执行或合并到更大版本；
    - 继续收集样本（触发但暂缓）。

## 5. 运行期固定产出物（Per-cycle Outputs）

> 为避免后续汇报只剩“散碎感受”，每个 observation 周期应按固定结构输出运行结果。

### 5.1 周期粒度

- 可按场景选择：
  - 时间维度（如每周/每两周一次）；
  - 样本维度（如每累计 20–30 个有效样本一次）；
- 粒度可以调整，但**每个周期都应产生一份结构化运行报告**。

### 5.2 固定产出物清单

每个 observation 周期至少输出以下内容：

- **1）本周期新样本记录概览**
  - 样本数量、scene 分布、page_type 分布；
  - 高频命中模板列表及使用场景简述。

- **2）模式聚类与变化**
  - 新出现或显著变化的模式簇：
    - 新模式：简要描述 + 典型样本 ID；
    - 旧模式：若有衰减/演化，也应记录。

- **3）触发条件评估结果**
  - 针对触发矩阵 A–E：
    - 标记“未触发 / 触发但暂缓 / 触发且建议立项”；
    - 若触发，附上一两句证据摘要与下一步建议。

- **4）候选池状态变化**
  - 新增候选项清单（名称 + 类型 + 来源样本）；
  - 状态变更（例如某候选项从“观察中”变为“冻结/放弃”）。

- **5）阶段任务包进度 %**
  - 针对当前阶段（Run-Phase1-ops），给出粗粒度进度：
    - 例如用“运行稳定性”“观察覆盖度”“文档同步度”等维度打分或备注。

- **6）长期总目标进度 %**
  - 面向整个 UI/UX skill 长期愿景，粗略评估：
    - Phase 1 全 scene 最小闭环完成度；
    - Phase 2 深化准备度；
    - 其它长期里程碑的相对位置。

- **7）当前所处阶段与下一触发条件**
  - 本周期结束时，明确写出：
    - “当前阶段仍为 Run-Phase1-ops / 是否计划调整”；
    - “下一阶段最可能被触发的条件及其当前进度”，例如：
      - 最近若干周期中，Trigger B（某 candidate 模式稳定胜出）距离阈值还有多少差距。

> 建议将上述 7 项固定为观察周期报告的“骨架模板”，方便后续 AI/人类对比不同周期之间的演化。

## 6. 当前默认不做的事项

> 目的：给运行期一个“默认不做”的清单，防止再次出现无边界扩建。

当前阶段（Run-Phase1-ops）的默认 **不做** 列表：

- **不开启第二批模板修复轮**
  - 即便已有候选模板，也需等待触发条件 A 或其它证据充分后，再单独立项。

- **不启动全面 Phase 2**
  - 不对全 scene 或大规模模板族进行系统性深度治理，仅允许在个别场景中做局部 Phase 2 试点（且需触发条件 E）。

- **不横向开新 scene 治理线**
  - 任何新 scene 的规范建设都应先进入候选池，并由 observation 证据支撑；当前不主动扩展 scene 范围。

- **不做全库规范审查**
  - 不再重跑一次“全库模板审查/修复”，只针对高价值/高风险资产，在证据驱动下做局部治理。

- **不主动修改 router / matrix / Guard / HTML 模板**
  - 除非触发条件矩阵中的某个条件被满足，且在运行报告中明确提出“建议动作”，否则一律不做结构性编辑；
  - 允许的改动仅限于文档回写、注释与 aria 层面的轻量增强。

- **不临时绕过 Guard 或手动硬改 router**
  - 对任何“快速绕过”的需求，应优先通过 observation 记录 + 候选池条目表现出来，而不是临时改规则。
